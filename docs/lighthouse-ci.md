# Lighthouse CI для Паркет36

Дата обновления: 2026-10-17.

Workflow: `.github/workflows/lighthouse.yml`.

Конфигурация: `lighthouserc.cjs`.

## Проверяемые страницы

- главная `/`;
- форма оценки `/zayavka/`.
- услуга `/uslugi/ciklevka-parketa/`;
- статья `/sovety/pochemu-skripit-parket/`.

Проверка запускается против локально собранной папки `_site`, поэтому не зависит от DNS, GitHub Pages и production Supabase.

## Категории и пороги

- Performance: ошибка, если медиана трёх результатов ниже `0.80`;
- Accessibility: ошибка при результате ниже `0.90`;
- Best Practices: предупреждение при результате ниже `0.85`;
- SEO: ошибка при результате ниже `0.90`.

Каждая страница измеряется трижды. Для Performance явно задан `aggregationMethod: 'median'`: проверяется средний по порядку балл, а не лучший из трёх. Best Practices сохраняет предупредительный порог. Accessibility и SEO блокируют PR при падении ниже минимального уровня.

17 октября одиночные CI-замеры главной дали 90 и 52 при одинаковом JavaScript и разнице общего веса страницы в 13 байт. Это не доказывает причину разброса. Для более устойчивой оценки включены три прогона, медиана и блокирующий порог; в отчётах сохраняются все исходные измерения. Дополнительно проверяются изменяемые типы страниц — услуга и статья.

Значения получены в GitHub Actions на локальной статической сборке. Они служат измеряемой отправной точкой, а не обещанием одинакового результата на каждом устройстве или сетевом соединении. Для подтверждения устойчивого эффекта используются последующие еженедельные запуски.

## Запуск

Workflow запускается:

- для каждого Pull Request;
- после изменения `main`;
- еженедельно;
- вручную через `workflow_dispatch`.

Локально:

```bash
npm install --no-audit --no-fund
python tools/build_pages.py
npm run test:lighthouse
```

## Отчёты

Lighthouse сохраняет HTML и JSON в `lighthouse-report`. GitHub Actions загружает папку как artifact `lighthouse-report` на 30 дней.

## Дальнейшая работа

Рабочая цель — мобильный Performance от 90 при устойчивых повторных измерениях. Блокирующий порог 80 — минимальная защита от заметной регрессии, а не целевой результат сайта.

Следующий анализ производительности должен проверять JavaScript, критический путь загрузки, объём HTML главной страницы и перенос обязательных элементов доступности из runtime-JavaScript в готовый HTML. Нельзя улучшать баллы искусственным отключением полезных проверок.
